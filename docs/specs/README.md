# 기능 및 화면 명세 (Specifications)

이 디렉토리는 프론트엔드 애플리케이션에서 제공하는 개별 기능과 화면의 사용자 요구사항, 인터랙션 흐름, 컴포넌트 계층, 클라이언트 상태 및 백엔드 API 연동 규격을 수집하고 관리하는 공간입니다.

---

## 스펙 작성 규칙

* **기능/화면 단위별 개별 파일 작성**:
  - 사용자 기능 또는 화면 단위마다 독립된 마크다운 파일로 분리하여 작성하며, 파일명은 `kebab-case.md` 방식을 사용합니다 (예: `auth-flow.md`, `pdf-viewer.md`, `workspace-dashboard.md`).
* **필수 프론트매터(Front-matter) 기재**:
  - 스펙 문서 최상단에는 반드시 아래의 YAML 프론트매터를 선언해야 합니다:
  ```yaml
  ---
  status: draft | review | approved | implemented | deprecated
  owner: <작성자 이름 / 핸들러>
  last-updated: YYYY-MM-DD
  ---
  ```
  - **status 값의 의미**:
    - `draft`: 요구사항 구상 및 초안 작성 중인 단계
    - `review`: 인터랙션 설계 및 API 연동 규격 검토를 거치는 단계
    - `approved`: 구현을 진행해도 좋다고 합의가 완료된 단계
    - `implemented`: 실제 컴포넌트, 상태 로직 및 테스트가 소스 코드에 최종 반영 완료된 단계
    - `deprecated`: 기능 개편이나 화면 교체 등으로 더 이상 유효하지 않은 스펙으로 분류된 단계

---

## 권장되는 프론트엔드 스펙 구조 (Recommended Sections)

1. **개요 (Summary)**: 기능의 목적과 사용자에게 제공하는 핵심 가치를 간결하게 기술합니다.
2. **목표 및 제외 대상 (Goals / Non-goals)**: 이번에 구현할 범위와 의도적으로 제외할 범위를 명확히 경계 짓습니다.
3. **유스케이스 및 사용자 흐름 (Use Cases)**: 사용자의 행동 시나리오와 화면 전환 흐름을 `UC-XX` 번호와 함께 기술합니다.
4. **화면 및 컴포넌트 요구사항 (UI / Component Specs)**: UI 상태(로딩, 성공, 빈 데이터, 에러) 매트릭스와 컴포넌트 구조를 정의합니다.
5. **클라이언트 상태 및 데이터 흐름 (State & Data Flow)**: 로컬 컴포넌트 상태, 폼 상태, 전역/서버 상태 캐싱 흐름을 명시합니다.
6. **API 연동 규격 (API Integration)**: 백엔드 `my-space-backend`에서 호출할 엔드포인트 경로, 파라미터, 요청/응답 타입 규격을 기술합니다.
7. **에러 핸들링 및 사용자 피드백 (Error Handling)**: 유효성 검증 실패, 네트워크 오류, 인증 만료 시 사용자 안내 방식(인라인 에러, 토스트, 폴백 UI 등)을 정의합니다.
8. **오픈 질문 (Open Questions)**: 추가 검토나 결정이 필요한 사항들을 정리합니다.

> [!IMPORTANT]
> **ADR과 Specification의 책임 분리**
> 프레임워크 선택, 상태 관리 라이브러리 도입 등 아키텍처적 기술 결정은 Specification에 직접 포함하지 않고 별도의 **[ADR](../adr/)**로 작성한 뒤 본 사양서에서 링크로 참조합니다.
